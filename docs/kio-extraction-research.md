# Extracting Polish KIO appeals, powers of attorney and bank transfers

Research for Odwołania2json, 21 November 2026.

**Start with native PDF text, Polish OCR for scans, and a different extraction schema for each document class.** Bank confirmations are a good first target for a CPU-only extractor. Appeals need a model or rules that can distinguish the challenged action from a similar action mentioned elsewhere. Powers of attorney need to preserve the relationship between a principal, its signers and the attorneys it appoints. A single PDF-to-JSON model is worth testing against this approach. The published comparisons below give reasons to run that test, but the winner on KIO documents is still an empirical question.

## What the benchmark leaders do

The closest broad comparison is Zhang et al.'s **ExtractBench**. It gives each system a document and a schema, matches repeated records, scores extracted values per document, and measures source grounding separately. It spans 370 documents, 4,869 pages and 67 document types. The table uses one snapshot of the maintainers' public results. Short means at most 10 pages and long means over 50. These scores describe enterprise documents across domains. [Paper and evaluation protocol](https://arxiv.org/html/2607.29677v1) · [Results CSV](https://raw.githubusercontent.com/run-llama/ExtractBench/main/leaderboard.csv)

The provider describes extra verification effort on complex documents. | 96.17 / 97.02 / 94.65 | Tied highest overall in the inspected table. Hosted service with public API and benchmark harness. The extraction engine is not released there. Use it as a performance reference. **Page parsing has a different leaderboard.** OmniDocBench v1.6 combines text edit similarity, table structure and formula recognition. Reading order has a separate score. On its English/Chinese-focused pages OXR-1.0 leads the published parsing table at 97.03, followed by TeleOCR at 96.91. PaddleOCR-VL-1.6 reaches 96.34. None of those scores tests whether an account belongs to the sender or an action date belongs to the first allegation. ## Research closest to the actual failure modes

**Polish people and roles in multi-page documents.** In PolEval 2020 Task 4, systems extracted company data and tuples of signature date, person and managerial role from financial reports. The winning CLEX system reconstructed layout from hOCR, found candidates using local rules, resolved them across the document and normalized the selections. It reached 0.651 test F1. In its development results, person names scored 0.805, while complete person records scored 0.607. This is a close precedent for evaluating a signer's name together with the principal represented. CLEX's GPL-3.0-or-later Java code is available. Its issuer dictionaries are specific to financial reporting. [Task and data](https://poleval.pl/2020/tasks/information-extraction/) · [Paper in the proceedings](https://poleval.pl/files/poleval2020.pdf) · [Official results](https://poleval.pl/2020/results/) · [Code and development breakdown](https://github.com/CLARIN-PL/clex)

**Polish OCR into canonical fields.** PolEval's 2026 PolOCRBench release contains 2,610 training image/reference pairs. Of these, 480 synthetic pages have field-level JSON for invoices, contracts and official correspondence. Real and degraded pages have transcription references. Use the first group to test exact amounts and identifiers, and the second to compare OCR degradation. The release includes neither the official test portions nor a baseline leaderboard. [Organizer data and release status](https://github.com/poleval/2026-polocrbench) · [Annotation formats](https://github.com/poleval/2026-polocrbench/blob/main/data/README.md)

**Grounding repeated and nested fields.** Perot et al.'s LMDX encodes OCR segments and their locations into the prompt. The model emits values with segment identifiers. A resolver maps them back to source regions and can reject unsupported text. The method handles scalar, repeated and hierarchical fields on VRDU and CORD. Its original evaluations used PaLM and Gemini. The transferable part is the segment protocol, implementable over an open model or LangExtract. Rossum's DocILE complements this with public code for testing field location and grouping line items. Evaluate who signed for whom the same way one evaluates which values belong to the same invoice row. [LMDX paper](https://arxiv.org/abs/2309.10952) · [DocILE paper and evaluation code](https://github.com/rossumai/docile)

**How to score nested JSON.** Ferguson et al.'s *ExtractBench* is a different project from Zhang et al.'s benchmark above. It pairs 35 PDFs with schemas and human annotations covering 12,867 evaluable fields. Its released evaluator assigns comparators by field and aligns records in arrays. It can separate a missed record from an invented one. Borrow its matching logic for diagnostics, especially on powers of attorney where list order can change. The UZP scorer's exact behavior remains unspecified. [Paper](https://arxiv.org/abs/2602.12247) · [Evaluator](https://github.com/ContextualAI/extract-bench)

**An existing KIO workflow.** An April 2026 UZP consultation describes a metadata service for formal review of appeals. Section 5.5 of the post-consultation specification groups extracted values by role and attaches quality and evidence to each field. It places signature and registry checks in separate workflow components. This gives an institutional precedent for an evidence view alongside the competition JSON. The published material describes a service contract. We found no public, reusable implementation of the complete KIO extractor or verified score on the hackathon's hidden cases. [UZP consultation](https://www.gov.pl/web/uzp/zaprojektowanie-implementacja-i-dostarczenie-narzedzia-wspierajacego-proces-oceny-formalnej-odwolan-wnoszonych-do-krajowej-izby-odwolawczej) · [Technical specification](https://www.gov.pl/attachment/e42cbf99-4374-42d5-86fa-a4845fb3215a)

## A pipeline to test on KIO

1. **Read pages and retain their coordinates.** Start with native words and boxes. Trigger Polish OCR on image-only regions, suspicious text encodings, or visibly populated regions with few words. Preserve page, raw text and box through every subsequent step. Use the first three pages to locate roles quickly, then search later pages for the first allegation, missing parties, or signatures.
2. **Route by content, with a rejection path.** Compare simple heading/layout rules with a character n-gram TF-IDF linear classifier. For example, a judgment can discuss an appeal and contain all its vocabulary. Check for judgment headings and operative text, an actual grant of authority, or sender/beneficiary/payment blocks. Use opaque filenames when testing. Tune rejection on held-out negatives. [Sparse text classification reference](https://scikit-learn.org/stable/auto_examples/text/plot_document_classification_20newsgroups.html) · [Official negatives](https://github.com/Urzad-Zamowien-Publicznych/hacknation-2026/tree/de135d20811caf630f3e94dc655ba5eebd9a6710/dane/negatywne)
3. **Extract fields by class.** Give the extractor the role and its neighboring blocks. Define the keys, accepted types, null policy, Polish examples, class cues and normalization rules in configuration. For ambiguous fields, send only the relevant sections with stable line IDs to the open model. If the evidence is elsewhere, expand the search to the rest of the document.

   | Class | Evidence to find | How to assemble the output |
   |---|---|---|
   | Appeal | Filing header, appellant and authority blocks, procurement reference and title, first allegation plus its immediately preceding factual context. In case 1 the operative cancellation and its date appear just **before** the numbered allegation. | Keep filing and action dates distinct. Map the first challenged act to the organizer's reason ID and look up its canonical description. Keep BZP, TED and internal procedure numbers separate. Distinguish the consortium leader, counsel and contracting authority. Preserve the specified nulls and 0/1 flags. [Appeal fields and reason dictionary](https://github.com/Urzad-Zamowien-Publicznych/hacknation-2026/tree/de135d20811caf630f3e94dc655ba5eebd9a6710/oczekiwane-json) · [Case 1 PDF and labels](https://github.com/Urzad-Zamowien-Publicznych/hacknation-2026/tree/de135d20811caf630f3e94dc655ba5eebd9a6710/dane/przyklad_01) |
   | Power of attorney | Separately identify who grants authority, who signs on that principal's behalf and who receives authority. Read the grant clause and signature blocks together. | Build one `mocodawca` record per principal, nest its `podpisujacy` list, and emit the separate `pelnomocnicy` list. The schema requests attorneys' names in the nominative. Keep the original phrase as evidence for each normalization. Case 1 has two recipients and one principal signer. [Field definitions](https://github.com/Urzad-Zamowien-Publicznych/hacknation-2026/blob/de135d20811caf630f3e94dc655ba5eebd9a6710/oczekiwane-json/pelnomocnictwo.json) · [Case 1 gold](https://github.com/Urzad-Zamowien-Publicznych/hacknation-2026/blob/de135d20811caf630f3e94dc655ba5eebd9a6710/dane/przyklad_01/pelnomocnictwo.json) |
   | Transfer | Locate payer and beneficiary sections, amount, operation date, transfer title and transaction reference. Read coordinates when columns interleave. | Bind each account to its label, preserve leading zeros, normalize the printed amount and date, and retain the complete title. In case 1 the PDF has a stamp-duty payment for a power of attorney, and the organizer supplies a positive transfer label. A filter that accepts only appeal entry fees loses this case. [Transfer fields](https://github.com/Urzad-Zamowien-Publicznych/hacknation-2026/blob/de135d20811caf630f3e94dc655ba5eebd9a6710/oczekiwane-json/przelew.json) · [Case 1 reference](https://github.com/Urzad-Zamowien-Publicznych/hacknation-2026/blob/de135d20811caf630f3e94dc655ba5eebd9a6710/dane/przyklad_01/przelew.json) |

4. **Verify role and value, then serialize.** Internally record the JSON path, raw quotation, page, box and normalization used. A literal value should be traceable to its role in that document. A derived reason ID should point to the factual passage and the dictionary entry. Duplicate names, account checksums and disagreements between documents are reasons to recheck the PDF. Keep canonical output and optional review evidence in separate locations so the batch output tree contains only expected files.

## How to choose the implementation

| Comparison | Hold constant | What would justify keeping the change |
|---|---|---|
| Native text + Polish Tesseract + class-specific rules, versus adding PP-OCRv6 or Docling on flagged pages | Same document split, routing and field extraction | More exact accounts, names or complete party records on scans and two-column layouts, with acceptable p95 time and peak RAM on the i7. |
| Rules alone, versus adding a grounded Bielik call on uncertain fields | Same OCR, source blocks, null policy and serializer | Higher end-to-end field F1 on first-action dates, reason IDs or role assignments. Record calls/document, tokens, latency and which rule errors the model introduces. |
| Grounded pipeline versus direct Qwen3.5-4B or NuExtract3 | Same held-out PDFs and target semantics, same treatment of failures | Higher F1 and complete-record accuracy at a size and runtime the organizers can accept. Break out short, scanned and multi-party cases. Avoid selecting a model on JSON validity alone. |

Split by **whole case**, keep identical and near-identical documents or template families together, and reserve unseen negative types. Measure routing independently and also count its mistakes in end-to-end scores. For a transparent local proxy, match repeated objects one-to-one within their parent, then count missing, spurious and incorrect field values. Report strict and normalized scores separately, including numerical amounts, identifier strings, null handling, party-role swaps, and false acceptance of unrelated attachments. Report field micro-F1, per-class results and the fraction of completely correct documents. Record OCR time, API time and peak memory separately. Public synthetic results and the organizers' hidden real-case result answer different questions.
